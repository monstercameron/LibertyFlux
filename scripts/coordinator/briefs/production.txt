This is a production lane: rewrite a batch of original game functions in Rust and prove each rewrite behaves identically to the original. Two timed pilots have already measured this work (their lanes are `p-01` to `p-10` and `q-01` to `q-20` under `{root}\.artifacts\scratch\`); read two or three of their `summary.txt` files and one `report.md` first, so you start from what they learned and not from zero.

{what}

How to check a rewrite: the project's checker is version 3 and lives in the repository: the driver `{root}\scripts\checker\checker2.py` (its module documentation at the top is the manual, written so that a production lane needs nothing else), the proof contracts in `{root}\scripts\checker\contracts` to copy from, and the runtime crate `{root}\crates\tools\lf-checker-rt` that rewrites are written against. `{root}\.artifacts\scratch\k-checker3\report.md` says what version 3 added and what it still cannot do. Follow the manual: a persistent 32-bit worker runs the original and the rewrite from identical starting state and compares return value, written memory, stack adjustment, outgoing calls and faults, driven by one contract file per function. Outgoing calls are intercepted and answered by script on both sides, so you do not rewrite callees: your rewrite must make the same calls with the same arguments in the same order through the checker runtime. Rewrites that read or call the original's code are reported as cheating.
- Never edit tracked files. Copy the driver into your own scratch folder and run the copy (it writes its verdicts next to itself), and make your rewrite crate depend on the runtime crate by its path in the repository. Version 3 gives each callee its own scripted answers or a sequence of them, answers written through pointer arguments, interception of calls made through registers, object function tables, data tables and tail jumps, pointer-aware comparison, thread-local state, vector-register arguments, and up to 40 compared call arguments. It marks a verdict vacuous, not passed, when too few trials ran to completion on the original or the function's calls never fired: a vacuous verdict means the contract is wrong, so fix the contract. If you still need something the checker lacks, add it to your own copy of the driver and describe the change precisely so it can be folded back.
- Use the version 3 worker executable already built at `{root}\.artifacts\build\cargo-tools\i686-pc-windows-msvc\release\lf-checker-worker.exe` as it is; do not rebuild it there (other lanes are running it). If you must change the worker, copy its crate into your scratch folder and build your copy into your own lane's build folder under a different crate name.
- Build your own crate with `--target-dir {root}\.artifacts\build\lanes\{lane}` so that fifty lanes do not queue on one build lock. Name the crate `{crate}`. Do not create a `target` folder anywhere else.

For each function, in order:
1. Disassemble it with capstone from `orig\GTAIV.exe` and work out its signature, the memory it reads and writes, the calls it makes and what it computes. Use what the project already knows: merged names in `m-names\symbols.json`, merged class layouts in `m-structures\structures.json` and the draft Rust types in `m-structures\lf_types_draft`, and for natives the per-native analysis named below.
2. First decide whether checker version 3 can verify it. If it cannot, do not spend time on it: record it as deferred with one of these exact reason codes and move on: `indirect_call` (calls through a register, an object's function table or a data table), `thread_local` (reads thread-local state), `frame_pointer_args` (passes pointers into its own stack frame to callees), `runtime_table` (depends on data the game fills in at start-up), `float_register_args` (takes or passes values in floating point or vector registers in a way the checker cannot script), `jump_thunk`, `not_a_function` (the listed start is not a real function entry: say what it is), `needs_encrypted_code`, `other` (explain).
3. Otherwise write the contract and the rewrite. The rewrite is clear, idiomatic Rust that expresses what the function does, with a doc comment, named constants and field names where known. It is your own implementation of the behaviour, not a transcription of instructions, and it is pointer-width independent wherever the function does not inherently depend on 32-bit layout.
4. Run at least 1,000 trials including edge values. Integers must match exactly, floats bit-exactly. Fix and retry on failure; stop after 6 attempts or 12 minutes on one function and record it as deferred with reason `other` and the detail.
Stop the whole lane after 110 minutes of work even if functions remain, and report which were not reached.

Output layout, identical for every production lane so the results can be merged by script:
- `out\rewrites\fn_<address as 8 hex digits>.rs`: one file per verified function, containing only that function, its doc comment, and a first line comment `// original: 0x<address> <name>`.
- `out\contracts\fn_<address>.json` and `out\verdicts\fn_<address>.json`: the checker contract and the verdict file it produced.
- `results.json`: a list with one record per function in your batch: `address`, `name` (the merged symbol name if one exists, otherwise your proposed descriptive name), `name_source` (symbols, native, proposed), `size`, `outcome` (verified, deferred, not_reached), `reason` (one of the codes above, for deferred), `detail`, `trials`, `attempts`, `minutes`, `rust_lines`, `checker` (write `v4`), `brief` (write `{brief_version}`), `mutant_caught` (true or false) with `mutant` (one phrase: what the wrong version changed), `narrowed` (a list of everything that made this function's comparison narrower than the default: a masked or skipped argument, a check switched off, a callee left to run natively, a raised call-log cap; an empty list if nothing), `calls` (how many outgoing calls), `touches_globals`, `uses_float`.
- `summary.txt` as usual: verified, deferred by reason code, not reached, total minutes, minutes per verified function, and anything the next lane should know.
The Rust you write is project code and may be published. The original's disassembly and bytes are not: keep them out of `out\`, the summary and any devlog fragment.
Change to the standard deliverables: this is routine production, so do not write `devlog-entry.html` unless you found something surprising that other lanes or readers should know (a bug in the original, a function whose behaviour contradicts its public documentation, a checker flaw that could pass a wrong rewrite). If you do, use the id `production-{slug}`.
