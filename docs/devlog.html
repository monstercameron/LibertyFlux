Tools: archives and compression

Every game archive now opens: all 49 package files and all 254 disc images list cleanly with a scripted tool, and the one build quirk found along the way, an encrypted sidecar file nobody had flagged, decrypts with the same method as everything else.

What was asked

Establish which container and compression formats this build uses from file headers, then find, test and where allowed install the tools to list and unpack them, and prove the pipeline by extracting samples.

What was found

Verified The build uses two package-file versions: the audio banks use the newer one and the player-model archives plus one small data archive use the older one. Nearly all disc images are encrypted; four small ones are stored open. All loose resources share one container version and are zlib compressed. No lossless-console compression appears anywhere in this PC build, and no package entry uses the format's own compression flag.

  • Package files list 3,522 contained files; disc images list 52,718 entries, with zero failures in either set.
  • Audio bank entries carry content hashes instead of names; a public hash table resolves 99 percent of them to readable names.
  • Scripts ship only inside archives: 941 compiled scripts across eight archives, none as loose files.
  • The small data archive was the surprise: unlike every other package file, its file content is encrypted as well as its table, and it decrypts to a readable text file.

Verified Tool results: the Rust archive crate builds but cannot open this build's encrypted tables, so it is not usable alone. The Python audio-bank library resolves names and extracts correctly for audio banks but misreads model archives. The classic C# archive browser was evaluated from its source only; it supports this exact game version but needs a desktop install. The zlib libraries in both languages inflate identical bytes.

What was decided or recommended

  • Scripted work should use the lane's small independent reader plus the Python crypto library: it is the only tested path covering all archive kinds, compression and the encrypted sidecar.
  • Audio-bank names should come from the MIT-licensed hash table behind a quiet wrapper.
  • Rust code should use the standard zlib crate; the LZX crate is recorded for console reference work only.
  • The desktop archive browsers stay owner-installed tools for interactive browsing, not part of the pipeline.

How to reproduce it

Verified Run the lane's listing script from the repository scratch area: it loads the archive key from the owner's executable into memory, validates it by trial decryption without ever displaying or storing it, then lists every archive into a JSON file and extracts a handful of small samples into the asset cache. The Rust check builds a scratch project against the archive crate and the compression crates and inflates one loose texture dictionary three ways for identical output.

What was confusing or went wrong

Verified Two naming traps cost time. The audio-bank name table looks empty at first because its entries are hashes, not broken offsets; comparing against the Python library's hash table confirmed the bytes match. The script-archive samples also came from an episode archive at first because its folder path ends the same way as the base path; per-archive counts in the report use exact matches. A first Rust attempt failed on a wrong argument type for the LZX crate and a bad relative path; both were fixed by reading the crate source and using an absolute path.

Subsystem survey: vehicles

Vehicle code is scattered across the executable rather than living in one module, with about one hundred thirty RTTI classes, six drivable vehicle types, and handling data held in plain structs with no RTTI at all. Helicopters and planes turn out to be subclasses of the automobile class, all network replication code for vehicles sits in the encrypted part of the file, and the shipped data files match binary format strings exactly, which gives the rewrite free parser tests.

What was asked

Survey the vehicle subsystem of the original executable by static analysis only: extract its RTTI classes with base classes and virtual table sizes, collect its strings, locate its code through relocation references, list its operating system and library dependencies, summarise public knowledge, note frame-rate dependencies, and write rewrite notes with a ranked list of what to understand first.

What was found

Verified The class tree is small and single-inherited: a base vehicle class with six descendants (automobile, bike, boat, heli, plane, train), plus a vehicle model info class, a factory, a scanner, task info, two network events, a paint shader effect, wheel render data, and two audio entities. Helicopters and planes derive from the automobile class, and the multiplayer mirror classes repeat the same shape.

Verified Handling, wheel, suspension, transmission, chassis, and siren classes do not exist in RTTI. Their behaviour is reachable through strings instead: six suspension position names, three transmission position names, per-wheel suspension health formats, force-transmission script tunables, wheel friction surface names, and a thirty-seven-field handling file with one hundred seventy-eight entries.

Verified One thousand fifty-nine code references cluster into one hundred fifty fine groups and fifty-two broader regions spanning the readable code, holding roughly eight hundred virtual methods as a firm lower bound and an estimated one to three thousand functions in total. The largest regions are vehicle and police audio, car driving and door tasks, drive-by flags with seat and door logic, damage audio, and the get-in and get-out task family.

Verified Vehicle code makes essentially no direct operating system calls; its dependencies are internal engine systems (physics, fragments, audio, rendering, tasks, networking, streaming). Third-party markers found are Bullet broadphase collision, zlib, Bink video, and NaturalMotion animation. Havok, PhysX, FMOD, Granny, SpeedTree, and Scaleform markers are absent.

Verified Six loose data files were read: handling data, vehicle definitions, car colours (hot-reloadable according to its own header), car groups per city district, vehicle extras with boat boarding points, and train camera nodes. A boat boarding-points format string in the binary matches the extras file line for line.

Verified Public bug reports tie vehicle behaviour to frame rate: acceleration and top speed change above ninety frames per second, helicopters and cameras misbehave past sixty, and the standard advice is to cap at sixty or thirty. The binary holds frame-lock settings, slow-motion effect names, and time-scale strings, but no explicit per-frame vehicle constants were found.

What was decided or recommended

Recover the handling, wheel, suspension, and transmission layouts from parser code and the data files rather than from RTTI, since no such classes exist. Rewrite in the order data parsers, factory and spawning, base vehicle update, automobile physics, per-type behaviour, tasks and events, audio glue, and networking last. Check file parsers, damage maths, task transitions, and packet units in the CPU emulator, and leave frame integration feel, deformation visuals, and multiplayer sync for the running game. Treat per-frame vehicle integration as frame-rate-sensitive until proven otherwise and validate handling at thirty, sixty, and above sixty frames per second.

How to reproduce it

Parse the executable headers for section and relocation tables, reuse the shared RTTI inventories of type descriptors and object locators, filter class names by vehicle keywords with a hand-pruned false-positive list, find virtual tables by scanning data sections for locator pointers, extract printable strings from data sections and filter by subsystem keywords, then join relocation targets in readable code against string and virtual table addresses and cluster nearby hits. Capstone spot checks over virtual method targets confirm each region holds real code.

What was confusing or went wrong

An early function-estimate lane had concluded the code section was unreadable on disk, but per-window entropy and disassembly showed clean code after the encrypted first megabyte, so the survey proceeded on the readable remainder. Keyword matching needed about ninety manual removals, with the worst offenders being mouse wheels, game clocks, uptown business districts, shader planes, and primary clans. One filter typo briefly hid a car-scream task class, and an animation keyword polluted the file-format group with over a hundred unrelated animation classes before it was fixed. All network vehicle code points into the encrypted range, so its size and behaviour stay unknown until emulator work begins.

Subsystem survey: networking

The executable still contains the complete multiplayer stack even though this edition removed multiplayer: entity replication, session management, presence and clan services, leaderboards, voice message types, and socket, HTTP and TLS transport. Games for Windows Live is gone without a trace, and the backend points at Rockstar Online Services instead. About half of the game replication layer appears to sit in the encrypted part of the code section, so it cannot be studied statically.

What was asked

Survey the networking subsystem from the executable alone: the classes, strings, code locations, operating system dependencies, public knowledge, timing behaviour, and rewrite notes, with a ranked list of what to understand first.

What was found

  • Verified Class names recovered through run-time type information show two layers: a game replication layer with per-entity-type sync wrappers, sync parsers, several dozen network event types, replicated task types, interpolation helpers, and array replication for pickups, player info and script variables; and an online services layer with session tasks, session events, wire message types, and a live-services manager with a Steam backend.
  • Verified Leaderboards dominate the class count: nearly fifteen hundred template bindings covering several hundred multiplayer mode schemas across ranked and standard boards for races, episodic content, team, competitive and co-operative modes.
  • Verified No reference to the old PC online platform remains anywhere: not in strings, class names, or imports. The replacement backend is named throughout: presence, party, invite, clan and sign-in events, matchmaking and clan web service endpoints, and Rockstar service hosts for auth, online services and cloud.
  • Verified Transport is raw sockets plus the engine's own HTTP client and statically linked TLS. Most socket imports are referenced from readable code in a select-loop client pattern with no listening sockets; all crypto imports are used for certificate checks and protected session-id storage.
  • Inferred The game replication layer and socket startup live mostly in the encrypted code region: most of its class tables and all of its diagnostic strings have no references from readable code. Session, presence, HTTP, stats upload and leaderboard code is in the readable region, in on the order of two dozen code areas totalling roughly a quarter of a megabyte.
  • Inferred Voice chat is a leftover surface only: message types, menu tokens and error text exist, but no voice transport was found, and the similarly named audio engine classes are unrelated sound synthesis voices.

What was decided or recommended

A rewrite should start with the pure serialisation pieces (bit buffers, message framing and ids, sync data layouts), then session state machines against a fake transport, and leave sockets, NAT traversal and the defunct server endpoints for last with loopback harnesses. The next step for this subsystem is to prove whether any network code is still reachable from the menus, and to recover sync data layouts from the readable parser code.

How to reproduce it

Parse the executable headers for sections, imports and relocations; scan read-only data for run-time type descriptors and validate complete object locators and class hierarchies against the relocation table; extract printable strings and filter by network keywords; resolve every relocation in the unencrypted code and keep targets matching network class tables, strings or socket and crypto import slots; group nearby hits into clusters; spot-check samples with a disassembler used only as a verifier.

What was confusing or went wrong

  • Verified The first clustering pass matched every class table in the binary instead of only network ones and produced hundreds of meaningless clusters; restricting targets to the curated network class list fixed it.
  • Verified Keyword filters kept catching false friends: police dispatch orders, gamepad names, menu selection tokens and sound synthesis voices all matched naive network keywords and had to be excluded by hand.
  • Unknown The exact third-party TLS library could not be pinned down: the cipher list suggests one family while an error string suggests another, and the version is unknown.

The script native table: just over three thousand natives, all named

Verified The executable registers 3034 script natives into a single hash table, and every one now has a name from public databases. The older of the two known name-hash generations is the common Jenkins hash and checks out on all 2878 old pairs; the newer generation, which this build uses, is still unidentified, though its hashes have an unusual two-halves structure that constrains the search.

What was asked

Find the script engine's native function table using byte patterns published by the open-source script debugger scrDbg, enumerate every registered native as a hash plus handler pair, confirm the name-hashing function, and name as many natives as possible against public name lists.

Verified Registration takes two shapes that both reach the same table insert routine: a small group carries its own failure check per native, while the large group calls through a shared wrapper that holds the check once. The table routines match the published open-table design entry for entry, including the probing rule and the empty-slot markers.

Verified Native name strings are absent from the executable, so scripts and the engine meet only through hash values. Seven cases where the two public databases disagreed on a hash were settled against the registered values: three favour one database, one was a misattributed name, and three turned out to be genuine alias pairs where both hashes are registered.

Inferred Roughly the first megabyte of the code section reads as high-entropy bytes rather than code, so it is likely decrypted by the start-up stub at load. Only the shared debug handler points into that region; everything else registered sits in readable code.

What was decided or recommended

  • The enumerated hash-to-handler list is the ground truth for this build's natives; later work should consume it rather than re-derive it.
  • The new name-hash algorithm stays open. The recommended next step is to extract the hashes that compiled game scripts actually call and attack the algorithm from those pairs, using the two-halves bit structure as the main constraint.
  • Handler code clusters into a few regions, which should make per-subsystem handler mapping straightforward.

How to reproduce it

  1. Search the executable's code for each published scrDbg pattern with wildcard bytes; each should occur once, pointing at the script-engine data.
  2. Read the table insert routine next to the table anchor and note its two-argument shape and probing loop.
  3. Find every push of a known native hash immediate followed by a call to the insert routine or its wrapper; pair each hash with the handler address pushed just before it.
  4. Match the collected hashes against the public SCO-Toolbox and HappinessMP lists to attach names, and hash the old list with the Jenkins function to confirm the old generation.

What was confusing or went wrong

Each hash in the small registration group appeared twice, which first looked like dual registration into two tables; disassembly showed the second push belongs to a failure-logging path, not a second table. The new hashes first appeared to have two bits structurally clear, which sent the analysis down a blind alley of masked and split-hash theories; the full-bit entries in the same list turned out to be old-hash placeholders, but the true new hashes really do keep those bits clear and the algorithm still resisted some sixty candidates plus seed-inversion, suffix, modulus and shift-family attacks. The shared debug handler points into the encrypted code region, so its runtime behaviour could not be checked statically.

GitHub Pages fails builds when pushes arrive seconds apart

Pushing once per commit broke the project site for several minutes. Of 28 site builds in the first hour of phase 0, 23 failed, each with a duration of zero seconds. The owner noticed before the coordinator did.

What was asked

The owner reported that the published site did not seem to be working. The pages returned normally when checked a few minutes later, so what had happened?

What was found

  • Verified The coordinator had just started integrating lane results one commit at a time, pushing after each. Twelve commits went up within about a minute.
  • Verified The build history shows each push starting its own site build, and every build except the last of a burst ending immediately with "Page build failed". Only the final push of each burst produced a working site.
  • Inferred A build that is still running is cancelled or rejected when a newer push arrives, and it is reported as a failure, not as superseded. While a burst is in progress the site can serve an old version or fail to load.
  • Inferred Each failed build probably also sends the repository owner a notification.

What was decided or recommended

  • Commits stay one change each, but a batch of commits is pushed once, after the last one. The agent rules and the commit tooling now do this.
  • The status tick makes at most two pushes: one for the batch of integrated lane results and one for the progress files.
  • After a batch, check that the newest build reports "built" before telling anyone the site is updated.

How to reproduce it

List the repository's Pages builds through the GitHub API and compare their creation times, statuses and durations with the times of the pushes.

Tools: models, textures and collision

Verified A working asset pipeline for models, textures and map placement now runs on the project machine: a community map extractor built from source converts game map archives to open glTF models and standard texture files, and the long-standing archive browser SparkIV runs for day-to-day inspection.

What was asked

Find, evaluate and where allowed install the tools the project needs for drawable, fragment, texture dictionary, collision, animation and map placement formats, test each one on this machine, collect the best public format documentation, and recommend which tool to standardise on for each job.

What was found

Verified Nine candidates were examined. Three were installed and tested successfully:

  • SparkIV, the archive browser and viewer for game archives, models and textures. The latest prebuilt release launches and stays running on this machine.
  • A community map extractor plus its pinned game-asset parsing library. It compiled with no errors and converted a small map sector (62 archive entries) into 41 out of 41 models with textures, with nothing skipped.
  • A Rust parsing crate for a newer game in the series. All 108 of its self-contained tests pass here. It cannot read this game's files directly, but its structure is the best template for a new loader.

Verified Four more were collected as reference but could not be fully tested: a Blender add-on whose code needs Blender itself (not installed), a maintained SparkIV source fork (the prebuilt release covers the need), and two recompilation-project resource readers, one without a licence statement and one under a restricted licence, so both are read-only references.

Verified The public wiki documents several formats field by field (drawables, collision dictionaries, placements, and the two text map formats), but the texture dictionary and vehicle fragment pages are stubs with no layouts; the parsing library source fills that gap.

What was decided or recommended

Inferred The project should standardise on SparkIV for browsing archives, the extractor plus parsing library as the asset pipeline, and a new clean-room Rust loader modelled on the Rust crate's design using the documented layouts. The closed-source editor OpenIV, the 3ds Max plugins, a paid modelling tool and Blender itself are left for the owner to install.

How to reproduce it

  1. Fetch the latest SparkIV prebuilt release from the project's own release page, unpack it into the tools folder, and launch the browser.
  2. Clone the map extractor and the pinned asset library revision, build the extractor with the installed .NET SDK, and run it against a copy-safe output folder with framework roll-forward enabled.
  3. Clone the Rust parsing crate and run its test suite with the Rust toolchain; no game files are needed.
  4. Read the public wiki pages for the drawable, collision, placement and text formats, and the parsing library source for the texture and fragment layouts.

What was confusing or went wrong

Verified One named Blender add-on repository no longer exists on its hosting site, so it could not be evaluated. One candidate name in the task turned out to be a different game series' recompilation project, not a texture tool; its resource reader was still useful as documentation. A first extraction test silently used an archive with no matching map files and produced nothing; re-running against a real map sector worked. The main closed-source editor's website showed an expired certificate on the day, so its details were confirmed from secondary sources instead.

Tools: audio and video

The project now has a tested open toolchain for all of the game's sound and video: FFmpeg reads every cutscene video, vgmstream reads the game's audio banks, and a small Python library extracts those banks from the archives. All sampled game audio turned out to be a single simple codec, which makes the port's audio job smaller than expected.

What was asked

Find, evaluate and where allowed install the tools the project needs for audio and video: the game's audio containers and codecs, speech and radio streams, Bink video files, and user music. Test whether vgmstream supports this game's PC audio, install a portable FFmpeg build and use it to identify the Bink files without converting them, identify the audio container format from headers, and name the Rust crates that could decode each format in the port.

What was found

Verified The game ships nine Bink version 1 videos: two long TV channels for the base game, four shorter ones for the two episodes, and three small clips. FFmpeg's Bink support reads all nine, reporting resolutions from 256 by 192 to 512 by 384 at about 30 frames per second, with Bink DCT audio at 22050 Hz (one small clip uses 11000 Hz mono; two clips have no sound).

Verified All game audio lives in encrypted RPF version 3 archives: forty in the base game plus three per episode. The entries inside are Rockstar AUD banks holding between one and over a hundred streams each. Every sampled bank, across ringtones, ambient radio, a music station and speech, uses IMA 4-bit ADPCM at 24000 to 32000 Hz. No MP3, Vorbis, XMA or Miles audio was found in the PC game audio path.

Verified vgmstream supports this game's PC audio: it reported correct metadata for all five sampled banks and decoded one stream to WAV. FFmpeg cannot open the AUD banks at all, so the two tools complement each other rather than overlap.

Inferred User music works by scanning a user music folder for WMA and MP3 files, and a small encoder program beside the game exports replay clips to Windows Media Video 9. Both conclusions come from program text strings, not from running the game. Unknown The exact folder path on a player's machine was not checked.

What was decided or recommended

The project should standardise on FFmpeg for video and Windows Media formats, vgmstream for inspecting and decoding game audio banks, and pyrpfiv for scripted archive extraction. The closed-source OpenIV editor is left as an optional install for the owner; nothing in this phase depends on it.

For the port itself, the lowest-risk path is the Symphonia crate family (MPL-2.0, pure Rust) for the ADPCM game audio and MP3 user tracks, plus a project-written AUD container reader, with FFmpeg bindings covering Bink video and the WMA edge case. There is no maintained pure-Rust Bink or WMA decoder, and the one Bink-aware Rust framework found is under the AGPL and therefore excluded.

How to reproduce it

Install a portable FFmpeg build from one of the Windows build sets linked on the FFmpeg download page, the command-line build from the vgmstream releases page, and pyrpfiv from PyPI. Point FFmpeg's probe tool at the game's movie files, extract audio banks from the sound archives with pyrpfiv using the owner's own game executable, and run vgmstream in metadata mode on the extracted banks. Full commands, versions and checksums are in the lane report.

What was confusing or went wrong

The extraction library's documentation names older game versions, but it parsed the current version's archives without complaint, so the version list is out of date rather than the code being broken. The same library prints thousands of log lines and fills in its file list through a side channel instead of returning it, which needed a small wrapper. The word ivaud, the community's name for the PC audio format, appears nowhere in the game executable, which briefly suggested the format might be absent until vgmstream identified the banks directly.

Subsystem survey: world, entities and object pools

The entity hierarchy survived intact in the executable's type data, but the world container, the pools and the population manager left no type traces at all, which means they are almost certainly static code with sizes baked in as plain numbers. Map data on disk uses text definition files plus binary placement files, and the public placement format matched the bytes on disk.

What was asked

Survey the world, entities and object pools subsystem working directly on the executable file: list its classes with base classes and virtual table sizes, collect its strings, locate its code through relocation references, note its operating system dependencies, check public documentation, note frame-rate dependencies, and rank what to understand first.

What was found

Verified The run-time type data holds thousands of classes, of which about two dozen belong to this subsystem. The entity tree runs from a common root through dynamic and physical entities down to objects, buildings, dummy placeholders, interior and portal instances, with seven model definition classes and a set of world query helpers.

Verified No trace of a world container, pool collection, population manager, file loader or placement class exists anywhere in the type data or the strings, so these are most likely static classes with no virtual tables. Pool sizes appear nowhere as text and must be plain numeric constants in code.

Verified Useful strings include pool exhaustion errors, population manager startup and shutdown messages, portal and room tracking text, placement provenance wording, level-of-detail distance settings, and pickup save and load errors. Map files on disk come in per-district triplets of definition, archive and binary placement files, and the placement header matches the public format documentation.

Verified Code references to this subsystem are scattered across the whole program by link-time code generation, with the densest spots around model definitions with portal tracking and around generic objects. About sixty direct references group into eighteen small clusters totalling tens of kilobytes, with a lower-bound estimate of roughly two hundred functions. Entity code itself calls no operating system functions directly; timing and threading calls live in neighbouring code.

What was decided or recommended

  • Start the rewrite with the model definition table and the text definition parser, then binary placement loading, then the pool allocator, then the world grid and scanners, then pickups, portals, population and detail policy.
  • Parsers, pool allocation sequences and handle encoding can be checked in a CPU emulator in isolation; streaming interplay, render equivalence and population timing need the running game.
  • Public format documentation for placement files is confirmed and can be relied on; pool capacities and the world grid layout are undocumented anywhere and are the highest-value unknowns.

How to reproduce it

Parse the executable's type descriptors, object locators and virtual tables from its data sections, extract printable strings, and join the relocation table against those targets, keeping only reference sites in the unencrypted part of the code section. Cluster nearby sites, validate standard function prologues with a disassembler, and curate out audio, interface, task, camera and network classes before clustering. Scripts and data files are kept with the survey.

What was confusing or went wrong

The first clustering attempt produced hundreds of meaningless clusters because audio, interface and task class names share the same substrings; only curation first made the picture usable. The encrypted first megabyte of the code section contains no relocation entries at all, so this method is blind there and the world and pool code may sit in that hole. One vehicle class slipped through a name filter and was caught on review.

Subsystem survey: streaming and resources

The streaming subsystem splits into a readable edge and an opaque core: 49 related classes were identified through type information, but the central file-device and archive code has all of its virtual methods in the encrypted part of the executable, while the media readers, one loader variant and the resource-dictionary plumbing are readable.

What was asked

Survey how the game loads assets at run time: the streaming request system, resource files and pointer fix-up, archives, file devices, asset dictionaries and memory budgets. The work was done by direct analysis of the executable file with Python, without the pending Ghidra analysis and without decrypting or running anything.

What was found

  • Verified 49 classes belong to this subsystem, 47 with measurable virtual tables totalling 597 slots. The file layer is a virtual filesystem family of 8 device classes with 34 to 38 virtual methods each: local disk, memory buffer, relative path remount, network stream, growable buffer, caching decorator, archive files and a streaming device.
  • Verified the pageable resource system centres on a small base class with 8 typed dictionary instantiations covering animations, textures, drawables, physics bounds, particles and render mesh fragments, plus typed cross-file references that are resolved at load time.
  • Verified the main streaming scheduler classes have no type information at all: no descriptors exist for the streaming controller, the streaming module, the asset stores, or archive and resource manager classes, so they must be static classes or plain structures and can only be found through strings and code references.

Why the route is direct to Rust

Lanes read decompiler output from a private folder and write Rust directly, with no committed C++ stage. Each rewrite is checked by running the original function and the Rust version in a CPU emulator from the same state. This follows from the owner's rule that no decompiled code may be committed, and from the goal that the game becomes 64-bit and portable.

The route changed three times

  1. Verified A from-scratch engine that loads the original assets. Rejected once the evidence showed that decompiling is fast and carries mission logic, AI and ragdoll behaviour across intact.
  2. Verified Decompile to C++, rebuild, then port to Rust. Rejected because only structures, symbols and Rust rewrites may be committed, so a C++ stage cannot be kept, and an uncommitted months-long intermediate is a loss risk.
  3. Verified Rewrite directly to Rust. Current route, and one phase shorter.

What the direct route costs

  • Verified Byte-matching against the original compiler is impossible for Rust, so every byte-matching tool in the reviewed projects is out. The check is an emulator comparison: results, memory writes and outgoing calls must agree. Both sides run in the emulator, so it does not depend on the game running on this ARM64 machine.
  • Verified The second check swaps accepted functions into the running game through an injected 32-bit DLL with a per-function switch. A regression is found by switching replacements off in halves.
  • Verified Known weakness: floating-point results can differ in the last bits, so those comparisons need a tolerance, and a tolerance can hide a real difference. The in-game switch is the backstop.
  • Unknown Whether the emulator comparison works at scale. It is our own design and no other project has proven it. The phase 1 gate of 50 accepted functions tests it.

Why Rust, and what that forces

Verified The Rust port exists to make the game 64-bit and portable to Windows x64, Windows ARM64 and macOS. That forces the following work, which is why 64-bit and renderer work wait until after phase 4.

  • Euphoria, the animation and ragdoll middleware, is statically linked 32-bit code with no source. It must be rewritten like game code.
  • Bink video needs a replacement decoder.
  • Resource files hold 32-bit pointers, so a converting loader is needed.
  • The script virtual machine needs pointer handles.
  • All Windows and Direct3D 9 calls go behind a platform layer.

Replacing functions inside the running game

The proven method in the GTA family is to build the rewritten functions as a DLL, load it through an ASI loader (a proxy DLL that loads plugin files at startup), and redirect each original function to its replacement with a switch per function. gta-reversed does this for San Andreas at 8,000 functions. Our second check has the same shape, with Rust in place of C++.

How gta-reversed registers and switches functions

  • Verified Registration contract: each class has a static function that registers its hooks, one central function calls them all, every function is installed with its address, and a function not yet reversed is marked so that it still calls the original (HookRegistration.md).
  • Verified Two-way hooks. Each hook can be switched between original and reversed at runtime, locked, restored to its previous state and written to a JSON file, and hooks are grouped by path (HookCategoryItem.cpp). An in-game debug menu toggles them.
  • Inferred Virtual functions are installed through a per-class macro taking the original virtual table address and slot count. The source is one pull request snippet whose body would not load.
  • Verified Layout assertions. Every reversed structure carries compile-time checks of its size and member offsets, so a wrong layout fails the build (Base.h). IV-SDK and the plugin-sdk GTA IV headers do the same.
  • Verified The injected build needs the exact expected executable bytes. A wrong build crashes randomly (gta-reversed-modern).

  • Timing: a 50 MHz guest timebase (a wrong value freezes every time-gated loading task), a 60 Hz vertical blank, a present gate that stalls when submitted frames exceed presented frames by 2, a frame counter in the device, and cooperative-polling status codes.
  • Render path: a RAGE layer over a Direct3D-style wrapper over command packets; immediate-mode draw begin, add-vertex and end; HUD draw commands as a 108-class hierarchy in a per-frame bump arena whose allocator sits in a thread-local slot; six named reflection resources (mirror at 320 by 180, environment paraboloid at 256).
  • Collision: load and fixup, composite expansion, bounding-volume bodies, simulation identifiers, a deferred insert queue, world bounds, axis-sweep quantisation, endpoint sort, a pair cache, filtering and narrowphase. The title-update build keeps a 500-slot bounds store with a flag-byte state machine scanned every frame (collision document).
  • Unknown Which script threads must run for the world to appear. Neither project documented it. Only the registration of script natives was mapped.

A lane is one agent working on one task in its own folder. The eight research lanes worked, but a lane that cannot run shell commands is limited to web reads, and long files were read only in part. Practices from other agent projects

  • Task size. Verified Thief 3 sizes work by function length, keeps workers under about 100 tool calls and never reuses a worker. Inferred The sources give the limits, not the reason. Our reading is that context decays in long sessions, so a fresh worker with a full packet beats a long session.

Upscaling, frame generation and ray-tracing denoisers

The four vendor frameworks cannot all be reached from one Vulkan renderer, and two of them are narrower than we assumed. The full reference, with a source link and a verified or inferred label on every claim, is the file documentation/upscaling-and-frame-generation.md in the repository. Read it before designing the renderer.

What changed in the plan

  • Verified DLSS 5 exists. NVIDIA's developer blog of 22 September 2026 describes it as neural rendering that needs an RTX 50 series GPU. The page does not say an SDK is available to developers, so the plan targets DLSS 4.5 through the Streamline SDK (NVIDIA developer blog). The coordinator opened this page.
  • Verified XeSS frame generation supports DirectX 12 only and works through its own replacement swap chain. XeSS upscaling supports Vulkan (XeSS frame generation guide). The coordinator opened this page.
  • Verified MoltenVK has no ray tracing in any release; the extensions exist only in an open pull request (MoltenVK pull request 2771). Path tracing on macOS therefore needs a native Metal backend.
  • Inferred DLSS is reported as unsupported on Windows on ARM64, and XeSS documents x64 only. FSR is the only candidate there and probably needs a rebuild from source.
  • Inferred MetalFX is reachable only through Metal. FSR on macOS is unconfirmed, so the macOS target lists MetalFX alone.
  • Verified Rust bindings: objc2-metal-fx is maintained; the DLSS and FidelityFX crates are new or placeholders; XeSS has none.

What the renderer must be designed for

  • Every temporal upscaler needs jittered low-resolution colour, depth, per-pixel motion vectors, exposure, and a reset signal on camera cuts.
  • Frame generation also needs the picture without the HUD, the UI separately, and control of presentation: DLSS, FSR and XeSS each bring their own swap chain.

Unknown The exact motion vector, depth and jitter conventions of each framework. The research lane's web reads truncated before those sections of the long guides. A lane with a working shell should read them from cloned repositories before renderer design starts.
