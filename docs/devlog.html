Native handlers LOCATE_OBJECT_3D to NETWORK_SET_HEALTH_RETICULE_OPTION: what they reveal

All 140 handlers in this batch are thin forwarding shims: they marshal script arguments, call one engine function, and store the result. The work pinned down the native call-context layout, identified the three shared handle-lookup helpers every lane will meet, and found that most network natives funnel through trampolines into still-encrypted engine code.

What was asked

Disassemble the handler of each native from LOCATE_OBJECT_3D to NETWORK_SET_HEALTH_RETICULE_OPTION, recover the call-context layout, describe what each handler does at engine level, propose names for the engine functions each handler calls, record any object fields touched, and flag stubs, shared handlers, and encrypted code.

What was found

Verified The call context is a small struct: offset zero holds the return-slot pointer, offset eight holds the argument-array pointer, offset twelve is a scratch-slot counter and offset sixteen starts sixteen-byte scratch slots. The word at offset four is never touched by any handler in this batch, so its purpose stays unknown.

Verified Handler shapes are uniform. About three quarters return a boolean or integer through two fixed instruction patterns, the rest return nothing, nine are pure tail jumps, and none is a stub: every handler reaches engine code. No handler reads global data or makes an indirect call, and none does pool lookups itself.

Verified Three handlers are shared. One serves eight platform and version-check natives, one serves eleven natives including version checks and copy-protection spot checks, and one is shared by the link-connected and rendezvous-success natives, which looks like a copy and paste alias.

Verified Six handlers reach engine code that is still encrypted on disk, including both shared platform-check handlers. Peeking one level down showed most network trampolines also land in the encrypted region, so the real network engine stays opaque for now.

Verified The shared helpers, seen by reading one call past the handlers: a script-handle to entity-pointer lookup used identically by the object, car and character mark-as-no-longer-needed paths with a per-type pool global; a player-index to player-pointer lookup; and a zero-argument gang-manager getter. Field findings include a fireproof flag byte and a cutscene-safe bit on the player struct, plus a must-equal-two mission-entity marker byte at a different offset per entity class.

Verified Two extended-config natives skip a four-byte script-side header word before handing a struct to the engine. Seven documentation gaps were found against the public native database, including one native with no entry at all and several where the handler reads more arguments than documented.

  • Proposed names were recorded for all 139 engine callees and six structure fields, with per-name confidence and reasoning, for the coordinator to merge.

Outputs are one JSON record per native plus proposed-name and proposed-field files.

Verified The first analysis pass misclassified argument reads as context reads because handlers reuse one register for both pointers; sequential tainting fixed it. A capstone version difference and a missing list append each cost one rerun. The lock-state argument of the car-door native looked boolean at first but mission scripts pass small integers, so it is an integer.

Native handlers HAS_CAR_BEEN_DAMAGED_BY_WEAPON to IS_CHAR_IN_ANY_HELI: what they reveal

All 139 readable handlers in this batch of 140 script natives were traced from handler to engine code, yielding 229 proposed engine function names and 62 proposed object fields. The headline results are the shared handle-to-pointer lookup used by two thirds of the batch, three entity pools told apart by usage, and a death-or-arrest check that always answers false.

What was asked

Analyse the batch of 140 natives from HAS_CAR_BEEN_DAMAGED_BY_WEAPON to IS_CHAR_IN_ANY_HELI: disassemble each handler, check the public native documentation and the decompiled mission scripts, describe what each handler does at engine level, and propose names for the engine functions it calls plus meanings for the object fields it touches.

What was found

Verified Every handler receives one call context: the return slot address first, then the argument array. Most handlers just forward script arguments to one engine function; two area checks share a generic unpack-and-call adapter instead.

Verified Nearly half the engine functions resolve script handles through one shared pool lookup, called with the pool and the handle, returning an object pointer or nothing. The three pools used here separate cleanly by native kind: one serves only character natives, one only vehicle natives, one only object natives. Two handlers do the same lookup inline, which confirms the pool layout of entries, serial bytes and stride.

Verified Damage tracking is shared across all entity kinds: every entity carries a last-damager link and a damaging-weapon value, and one setter links victims to damagers while marking per-player damaged flags. Two player natives read exactly those flags, closing the loop.

Verified Several queries are one-shot: the photographed flags for characters and objects, the vehicle resprayed flag and the global resprayed event all clear themselves when read. The dead and injured queries return true for invalid handles, as documented.

Verified The death-or-arrest check always returns false: it runs its update work and then answers no unconditionally, so scripts call it for the side effect. It appears in hundreds of mission scripts.

Verified One heading check ignores the argument its handler passes and only compares a global value. One frontend text native is a bare two-instruction global reset that ignores the call context entirely.

Verified Four natives, including the region check and the motion-control reload check, funnel into one helper in the encrypted part of the executable, so their behaviour stays unknown. Both are publicly documented as always returning false. A few other natives (camera collision, on-screen test, network id checks, some task checks) also bottom out in encrypted code.

Inferred Fixed gameplay constants read out of the code include the pickup search radius, the tyre burst health, the door-open angle, the upright and upsidedown tilt limits, and two special weapon ids that match whole weapon categories instead of one weapon.

Rust reader: compiled scripts (SCO) and a disassembler

A new Rust crate loads every shipped compiled script and disassembles it: all 941 scripts parse and fully decode with zero failures, and native calls resolve to names through the engine native table.

What was asked

Write a clean Rust reader for the compiled script format with a disassembler: header, code, statics, globals, native calls and encryption, verified against the real game files, with native names loaded from a data file at run time rather than embedded.

What was found

Verified All but one shipped script share a single encrypted container version; the exception is an unencrypted leftover from an older container version that decodes with the same instruction set.

Verified The corpus holds about fourteen and a half million instructions with roughly seven hundred thousand native calls to about twenty four hundred distinct natives, of which over ninety nine percent resolve to names.

  • Most called natives are injury and death checks, debug print helpers, the game timer and the wait helper, matching an independent count made from the older decompiled reference set.
  • Five fixed opcodes never appear in any script, including the two exception opcodes, and small-constant pushes above thirty one are never used.
  • Only six scripts declare a globals segment, in per-episode pairs.
  • The header signature word is one constant per episode, not zero-everywhere as the public wiki suggests.
  • Nineteen called native hashes are not registered in this build; eight of them sit in the stale leftover script and the rest look like dead code paths.

Verified Two scripts disassembled with this crate match an independent open-source disassembler instruction for instruction.

What was decided or recommended

The crate is ready for review and integration: it parses from byte slices with explicit little-endian reads, returns typed errors instead of panicking, keeps the decryption key in memory only, and carries unit tests plus a game-data integration test. Next steps are attributing the unregistered native calls to live or dead code paths and mapping carved scripts back to archive file names once the keyed archive reader lands.

How to reproduce it

Build and test the crate in the usual way, then run the integration test with the game folder environment variable set to parse and disassemble all scripts, optionally writing the per-script statistics file. The example binary summarizes a single script file to standard output and never writes game content anywhere.

What was confusing or went wrong

Inferred The most confusing source was an instruction-set document inside an otherwise reliable open-source tool repository: it describes a newer script target, not this game's, while the repository's code for this game's target is correct. The crate follows the code.

The first corpus run silently missed the leftover script because the test only scanned for the current container version; reading that archive's entry directly exposed the older magic. A debug-mode key search took minutes where a release build takes seconds, and a shell default wrote reference output in an unexpected encoding that broke the first comparison.

Class layouts: remaining game classes, first half by name

Layouts were recovered for the first half of the remaining game classes: about two thirds of their code sits in the encrypted part of the executable and could not be analysed, but virtual interfaces, constructor patterns and size estimates were recovered for the rest, including an odd case where derived destructors store the base class table address.

What was asked

Recover object layouts and virtual interfaces for 137 classes: per-slot virtual tables, constructors and destructors, object sizes, field offsets and kinds, and relationships, working only on the unencrypted code with a relocatable-reference search.

What was found

  • Verified 137 classes hold 2,072 virtual slots; 64 percent point into the encrypted range and were not analysed.
  • Verified 61 constructors, 13 deleting destructors and 49 factory-style creator functions were identified; 470 field observations were recorded, most of them low confidence single sightings.
  • Verified the render-command family (14 tiny classes) is allocated 12 or 16 bytes at a time through a shared allocator, which pins their sizes.
  • Verified the eight effect classes derived from the 2d-effect base get their sizes (16 to 168 bytes) from array-destructor stride measurements, since their own code is encrypted.
  • Verified the network-event and entity-parse families are fully encrypted with no references in readable code, so nothing beyond table shape is known about them.
  • Inferred a large dispatcher routine referencing seven task-descriptor tables is a task factory, not a destructor as first labelled.
  • Unknown why the derived effect destructors store the base class table address rather than their own.

What was decided or recommended

Rewrite in this order: the tiny render commands first, then shader effects and cutscene events, then task descriptors once their bases land, then headers-only for the effect family, and the encrypted network and parse families last. Sizes from destructor strides outrank sizes from field offsets where they disagree.

How to reproduce it

Scan the executable relocation table for code sites whose stored value equals a class table address, decode each site instruction, and classify the containing function by whether it stores the table through the object pointer, an alias, a fresh allocation, or a global. Slot override analysis needs no disassembly: compare each slot target with the base class tables.

What was confusing or went wrong

An early decoder took the first instruction covering a reference site and misclassified several creators; verifying each decode against the relocation value fixed it. A destructor heuristic misfired on the task factory until its body was read. Allocation-size guesses below four bytes turned out to be argument noise and were discarded.

How to reproduce it

Find every virtual table address stored into an object by scanning the relocation table for code locations whose value equals a known table address, map each site to its function with the function inventory, and disassemble with capstone while tracking which registers hold the object pointer. Attribute a function to a class only if its first table store (destructor) or last table store (constructor) is that class's table and every other store at offset zero names a strict base class; anything else is inlining or a factory. Classify readable slot bodies by shape: table store means destructor, single load means getter, calls only means forwarder.

What was confusing or went wrong

Two silent bugs wasted the first runs: wrong capstone operand-type constants dropped every memory access, and adding the relocation block base twice (the library already returns full addresses) hid all but two of the table references. The disassembler also ran past function ends into neighbours until it learned to stop at padding and known entries. The stranger findings are that the root base class seems to embed a subobject of its own kind, that dozens of functions mention one template's table without ever storing it, and that the whole file-device and parsing trees are dark while their close cousins are readable.

Class layouts: animation, motion tree and Euphoria

All 148 animation, motion tree and Euphoria classes now have recovered object layouts: constructors, destructors, field maps and size estimates derived from the unencrypted code, with the worst gaps flagged rather than guessed.

What was asked

Recover the object layouts and virtual interfaces of the animation family: which virtual slots each class overrides, which functions construct and destroy it, how big it is, what lives at each field offset, and how the classes relate. Work only on the unencrypted code.

What was found

Verified Every class in the batch was matched to its runtime type record, yielding 149 virtual tables. Scanning the unencrypted code for references to those tables found 466 use sites in 313 functions, of which 309 were confirmed to store a table address into an object under construction. In total 319 constructors and 78 destructors were classified, 38 storing functions stayed ambiguous, and 2291 field records were extracted.

Verified The family splits into clean sub-hierarchies: eighteen behaviour classes share one eight-slot base, thirteen animation channel codecs share a 21-slot base, sixteen motion tree nodes share a 14-slot base with three nodes adding a fifteenth slot, and the effector, creature component, frame filter and request families each share uniform table sizes. Slot zero is the destructor in every family checked, and deleting destructors appear in both scalar and vector forms.

Verified Only six percent of distinct virtual function bodies live in the encrypted range, but they cluster in base-class tables: shared core implementations are encrypted far more often than per-type overrides. Two classes are fully opaque (one network event with all 24 slots encrypted, one joint data class), and seven classes show no construction code at all in the visible range.

Inferred Several slots returned small constants or per-class static descriptors when examined: motion tree nodes expose a descriptor whose first field is a per-class numeric id, channel codecs return small type numbers, and effectors expose pointer and float getters consistent with target handles and weights. Meanings for most other slots remain unknown.

Inferred Object sizes range from a few bytes for empty shells and simple requests up to around eight hundred bytes for behaviour objects and several kilobytes for frame buffers. About thirty sizes are confirmed by allocation sites; the rest are lower bounds from the highest field touched. Base-class sizes that exceed their smallest derived class are flagged as overestimates caused by inlined construction.

What was decided or recommended

Layouts are recorded per class with per-field confidence and evidence, in a machine-readable structures file for later rewrite work. The recommended rewrite order is channel codecs first, then frame degrees of freedom and filters, then motion tree nodes and requests, then the game animation layer, then effectors and creature components, then the ART framework and behaviour objects, and finally the composers and physics glue, which hold the most encrypted code. Public header collections were checked and contain no usable layouts for this family, so everything rests on the binary evidence.

How to reproduce it

Join the batch class list to the RTTI class and table inventories by mangled name. Collect every relocated position in the unencrypted code whose stored value equals one of the family table addresses. Map each to its containing function from the unified function inventory, disassemble with capstone, and track the object pointer starting from the thiscall register while also promoting any register that receives a table store. Classify each virtual slot body by its opening instructions, merge field accesses across each class's own methods, and estimate sizes from the highest offset touched, cross-checked against allocation-size constants.

What was confusing or went wrong

  • A relocation bug initially found one table reference instead of 466: the page base was added to a value that already included it. Checking the library's actual semantics fixed it.
  • A capstone bug made every constant-returning function appear to return 19: reading the immediate field of a register operand yields the register id. Spot-checking raw bytes caught it, and the corrected values (type ids, sizes, descriptor pointers) proved far more useful.
  • Optimised code often passes the object in registers other than the usual thiscall register, which first hid a third of the constructors. Treating any register that receives a table store as the object pointer recovered them.
  • Derived constructors inline their base construction, so base-class field sets are polluted with derived-class offsets. Suspect sizes are flagged in the data rather than silently reported.

Engine behaviours to confirm on PC, not assume

Verified The projects documented the following for the Xbox 360 build. Unknown Each is unconfirmed for the PC build, which was designed around different memory and a different thread model. Sources: runtime behaviour, the playbook above, the streaming document and the rendering research.

  • Boot: the engine's entry function runs once, where the console runtime called it repeatedly and a recompilation must supply the loop. Then a frame tick, a ready check, a call that starts nine workers and the subsystems, one call that initialises 63 subsystems, a loading gate, and a main loop under an orchestrator that ends in a present.
  • Threads: nine workers (two render, three streaming, three resource, two GPU), a special thread with a 256 KB stack, a vertical-blank path, an audio stream worker and a separate audio render driver, and content-enumeration threads. The render workers block by design.
  • Streaming: a registry of 24-byte records with a four-state machine, recursive dependency acquisition, 8 fixed load slots, a synthetic stream path by index, per-worker rings of 16 positions (15 usable, reads up to 32 KiB), file-device layers for disc and hard-disk cache, and per-type fixup callbacks.   • Render path: a RAGE layer over a Direct3D-style wrapper over command packets; immediate-mode draw begin, add-vertex and end; HUD draw commands as a 108-class hierarchy in a per-frame bump arena whose allocator sits in a thread-local slot; six named reflection resources (mirror at 320 by 180, environment paraboloid at 256).
  • Collision: load and fixup, composite expansion, bounding-volume bodies, simulation identifiers, a deferred insert queue, world bounds, axis-sweep quantisation, endpoint sort, a pair cache, filtering and narrowphase. The title-update build keeps a 500-slot bounds store with a flag-byte state machine scanned every frame (collision document).
  • Unknown Which script threads must run for the world to appear. Neither project documented it. Only the registration of script natives was mapped.

Upscaling, frame generation and ray-tracing denoisers

What changed in the plan

  • Verified DLSS 5 exists. NVIDIA's developer blog of 22 September 2026 describes it as neural rendering that needs an RTX 50 series GPU. The page does not say an SDK is available to developers, so the plan targets DLSS 4.5 through the Streamline SDK (NVIDIA developer blog). The coordinator opened this page.
  • Verified XeSS frame generation supports DirectX 12 only and works through its own replacement swap chain. XeSS upscaling supports Vulkan (XeSS frame generation guide). The coordinator opened this page.
  • Verified MoltenVK has no ray tracing in any release; the extensions exist only in an open pull request (MoltenVK pull request 2771). Path tracing on macOS therefore needs a native Metal backend.
  • Inferred DLSS is reported as unsupported on Windows on ARM64, and XeSS documents x64 only. FSR is the only candidate there and probably needs a rebuild from source.
  • Inferred MetalFX is reachable only through Metal. FSR on macOS is unconfirmed, so the macOS target lists MetalFX alone.
  • Verified Rust bindings: objc2-metal-fx is maintained; the DLSS and FidelityFX crates are new or placeholders; XeSS has none.
