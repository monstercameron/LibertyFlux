What the executable shows: a first look at its headers

The Steam build is a 2023 rebuild made with Visual Studio 2012, its main code is not encrypted, class names are present, and link-time code generation was used. That settles several open questions and confirms one risk. Everything here comes from the file's headers, read with the Python pefile library. No code was disassembled for this entry.

What was asked

Which exact build are we working on, what compiled it, is it packed or protected, does it carry class names, and what does it depend on at run time?

What was decided

  • Try Ghidra's stock Visual Studio 2012 signatures for tagging library code before building any of our own.
  • Treat link-time code generation as confirmed when designing the queue and the comparison: do not assume a function's arguments arrive the standard way.
  • Understand the start-up stub before the harness phase. It is now an explicit unknown.
  • Audio and input replacements target what DirectSound and DirectInput provide, not XAudio2 or XInput.

How to reproduce it

Copy the executable into the ignored orig folder and read it with pefile: file header, optional header, section table with per-section entropy, parse_rich_header(), the debug directory, and the import and delay-import tables. Count type descriptors by searching for the byte string .?AV. No Ghidra run is needed for any of this.

Why the route is direct to Rust

Lanes read decompiler output from a private folder and write Rust directly, with no committed C++ stage. Each rewrite is checked by running the original function and the Rust version in a CPU emulator from the same state. This follows from the owner's rule that no decompiled code may be committed, and from the goal that the game becomes 64-bit and portable.

The route changed three times

  1. Verified A from-scratch engine that loads the original assets. Rejected once the evidence showed that decompiling is fast and carries mission logic, AI and ragdoll behaviour across intact.
  2. Verified Decompile to C++, rebuild, then port to Rust. Rejected because only structures, symbols and Rust rewrites may be committed, so a C++ stage cannot be kept, and an uncommitted months-long intermediate is a loss risk.
  3. Verified Rewrite directly to Rust. Current route, and one phase shorter.

What the direct route costs

  • Verified Byte-matching against the original compiler is impossible for Rust, so every byte-matching tool in the reviewed projects is out. The check is an emulator comparison: results, memory writes and outgoing calls must agree. Both sides run in the emulator, so it does not depend on the game running on this ARM64 machine.
  • Verified The second check swaps accepted functions into the running game through an injected 32-bit DLL with a per-function switch. A regression is found by switching replacements off in halves.
  • Verified Known weakness: floating-point results can differ in the last bits, so those comparisons need a tolerance, and a tolerance can hide a real difference. The in-game switch is the backstop.
  • Unknown Whether the emulator comparison works at scale. It is our own design and no other project has proven it. The phase 1 gate of 50 accepted functions tests it.

Why Rust, and what that forces

Verified The Rust port exists to make the game 64-bit and portable to Windows x64, Windows ARM64 and macOS. That forces the following work, which is why 64-bit and renderer work wait until after phase 4.

  • Euphoria, the animation and ragdoll middleware, is statically linked 32-bit code with no source. It must be rewritten like game code.
  • Bink video needs a replacement decoder.
  • Resource files hold 32-bit pointers, so a converting loader is needed.
  • The script virtual machine needs pointer handles.
  • All Windows and Direct3D 9 calls go behind a platform layer.
  • The renderer must output motion vectors, depth and jitter for upscalers.
  • Inferred Path tracing on macOS would need native Metal, because MoltenVK does not expose ray tracing as far as we know.

Xbox 360 static recompilation against function-by-function rewriting

Inferred Lane D compared the routes. Its facts about the 360 projects come from their repositories (XenonRecomp, LibertyRecomp RAGE API). Its PC column is its own assessment. It concluded that the 360 route is the better base for a quick playable port and the worse base for reconstructing source.

Dimension Xbox 360 recompilation PC rewrite

Rust suitability Hostile. Big-endian memory, reversed vector lanes and goto control flow would carry into Rust. Clean. Only names and layouts come from the 360 side.

Harness design taken from other projects

Thief 3 (MSVC 7.1, x86) has the closest toolchain and the most developed agent harness, so the plan copies its structure. The parts that make a compiler reproduce original bytes do not apply, because Rust cannot. The byte-match gate is replaced by the emulator comparison.

Parts taken, with the real numbers

  • Verified Queue. A script orders functions easiest first and lanes do not choose. Thief 3 scores instruction count plus 3 per branch, 2 per call, 10 per switch, 10 per exception frame and 1 per x87 instruction (next.py). Snowboard Kids 2 later fitted its weights by logistic regression, and stack size predicted nothing (blog).
  • Verified Claims. One file per claimed function, created atomically, expiring after 2 hours and renewed by every attempt.
  • Verified Context packet: the target, resolved references with names, structures touched, the most similar accepted functions with source, names that accepted callers already use, the family, and the best earlier attempt on a second pass (context.py).
  • Verified Attempt budget: cap of 12 per claim, stop after 4 counted attempts with no new best. The code comment cites replayed ledgers: 3 would have refused 10 of 1,219 matches to save 36 attempts, and 4 refuses 2 to save 18 (common.py). Inferred Another lane read the workflow document and recorded 3, so sources disagree. The code is more likely current. Snowboard Kids 2 reportedly gives up after about 30 attempts, seen only in a fork.
  • Verified Deferral is a normal outcome, recorded with a blocker tag. Permanently unworkable functions move to an exclusion list.
  • Verified Routing by size. Functions up to 31 bytes: 20 per worker, cap 5. From 32 to 79 bytes: by class, cap 8. From 80 bytes: the stronger model, cap 10. A second pass uses the other model. Workers stay under about 100 tool calls and up to 20 run at once.
  • Verified Families. Functions identical after masking references are grouped. One accepted member is stamped onto the rest and passed through the same gate with no model call.
  • Verified Guard rails live in tooling. Thief 3 workers write only under a scratch folder and run only four scripts, enforced by a pre-tool hook that also denies git (guard-settings.json).
  • Verified A lint runs on every candidate, and every batch ends with a sweep that releases stale claims and appends cost, attempts and deferral reasons to a ledger.
  • Verified Smaller ideas. Nigel defines a lane as a candidate command, a prompt template, and verify, success and reset commands (README). The asmlift prompt demands two deliverables of equal standing: merged work and a tool defect log ranked by cost.

What applies to us

Replacing functions inside the running game

The proven method in the GTA family is to build the rewritten functions as a DLL, load it through an ASI loader (a proxy DLL that loads plugin files at startup), and redirect each original function to its replacement with a switch per function. gta-reversed does this for San Andreas at 8,000 functions. Our second check has the same shape, with Rust in place of C++.

How gta-reversed registers and switches functions

  • Verified Registration contract: each class has a static function that registers its hooks, one central function calls them all, every function is installed with its address, and a function not yet reversed is marked so that it still calls the original (HookRegistration.md).
  • Verified Two-way hooks. Each hook can be switched between original and reversed at runtime, locked, restored to its previous state and written to a JSON file, and hooks are grouped by path (HookCategoryItem.cpp). An in-game debug menu toggles them.
  • Inferred Virtual functions are installed through a per-class macro taking the original virtual table address and slot count. The source is one pull request snippet whose body would not load.
  • Verified Layout assertions. Every reversed structure carries compile-time checks of its size and member offsets, so a wrong layout fails the build (Base.h). IV-SDK and the plugin-sdk GTA IV headers do the same.
  • Verified The injected build needs the exact expected executable bytes. A wrong build crashes randomly (gta-reversed-modern).

How those projects verified

  • Verified There is no test suite. A fork's instructions say testing is injecting the DLL and checking behaviour in the game. The layout assertions and the runtime switch are the whole mechanism.
  • Inferred re3 began in 2018 as single-function replacement by DLL to test reversed collision and physics inside the original game, and went standalone around April 2020. Search snippets only, because the original repository is gone.
  • This is why the emulator comparison exists. It catches what in-game playing misses, and it runs without the game.

Hooking notes

  • Verified MinHook 1.3.4 supports x86 and x64. safetyhook is C++23 for Windows x86 and x86_64. retour is a Rust fork of the detour crate: static_detour needs nightly, thiscall support needs rustc 1.73 or later, and its CI covers the 32-bit Windows target (retour).
  • Inferred A hook for a thiscall method (the C++ convention that passes this in ECX) is written in the fastcall shape with a dummy parameter for EDX. Three practitioner sources agree.
  • Verified Rust's 32-bit Windows target built a DLL exporting an extern "thiscall" function. Current Rust requires #[unsafe(no_mangle)].
  • Verified GTA IV needs the 32-bit ASI loader installed as dinput8.dll (setup notes). FusionFix finds code by wildcard byte patterns and installs mid-function hooks (example), but old patterns still fail on new builds, as the next entry shows.
  • Inferred To record a function's inputs and outputs from the real game, Frida's Interceptor is the standard tool. x32dbg has conditional tracing commands (index).
  • Unknown No guide to hooking by virtual-table slot was found.

What is already known about the GTA IV executable

The target is the Steam Complete Edition executable (1.2.0.x). Most public knowledge targets older builds, and byte patterns do not carry across builds, so names must travel by other means. No symbols exist for the PC executable.

Versions and tool support

Version Known Tools

Why the Steam build, and what that costs

  • Verified The owner has it and it runs without a cracked launcher. Downgrading needs a cracked launcher, which the project will not use (PlayGTAIV README). The 1.0.8.0 executable is used only for static analysis, if an official patch executable is available, so that Ghidra Version Tracking can carry names across.
  • Verified Older patterns do not transfer. An audit found nine of nine older ZolikaPatch signatures matched nothing on 1.2.0.59 (audit). Plan on semantic ports and version tracking.
  • Unknown Whether the executable is packed or wrapped in a way that blocks Ghidra. No source says so and none says otherwise. The game is not installed yet.

Naming sources

  • Verified About 3,000 script natives exist. Cross-check three databases: sannybuilder gta_iv.json (1.3 MB, typed), HappinessMP natives and a 44 KB natives.json in RAGEStuffIReversed. Inferred Some entries are debug natives stripped from release builds.
  • Verified IV-SDK and IV:MP (both GPLv3) hold about 40 or more hand-written class headers with offsets. The plugin-sdk GTA IV tree is thin and zlib-licensed. Read for names and layouts, copy no code.
  • Verified A community Hex-Rays database (25.6 MB, no licence) exists. No PDB or symbol package was found.
  • Inferred Class names from runtime type information probably survive in the PC build, as on the Xbox 360. binkw32.dll and xlive.dll look dynamically linked, from missing-DLL reports. Other static libraries are unconfirmed.

Script engine and resource formats

  • Verified A game script thread is the base thread plus a 24-byte program name and flags. scrDbg and IV:MP agree on the offsets. Natives sit in an open-addressing hash table keyed by name hash. Threads run on an instruction budget. Globals are not paged, unlike GTA V. scrDbg finds all of it on the Complete Edition with ten byte patterns (scrDbg).
  • Verified The compiled script format has a 24-byte header, 79 opcodes plus push, and encrypted variants (SCO). Compiling with the wrong per-version natives mode silently mistranslates every native call.
  • Verified Resource files are literal memory images. Pointers are a 28-bit offset plus a 4-bit block type across a virtual and a physical segment, fixed up at load. Three independent sources agree. This is why a 64-bit build needs a converting loader. Structures inside a file can be identified by the virtual table values the resource compiler wrote.
  • Verified Archives: RPF2 for the main game, RPF3 for audio, IMG3 for streaming. An Unlicense Rust crate reads and writes them (rpf-archive-rs). FiveM's loader is reference only.

Confirmed absent

  • Verified No public PDB, no Ghidra or IDA script collection for GTA IV, no CitizenIV source, and no repository at the claimed ElCapor gta4-modern address (HTTP 404).
  • Verified No surveyed source documents the render thread split or Euphoria integration. Both need first-hand analysis.

What the Xbox 360 recompilation projects give us

They give class names, virtual table layouts and written-down engine knowledge. They do not give code or real function names, and the much-quoted analysis database was not confirmed to exist publicly. Names can move from the 360 binary to the PC binary by matching virtual table slot order, the one method that works across instruction sets.

The analysis database claim

  • Inferred Search snippets quote the LibertyRecomp build document as describing a database of 31,782 functions, 3,332 RTTI classes and 51,494 symbols, with decompiled pseudocode, served to agents by a tool server. The file section would not render, so the quote was not read in place.
  • Verified The database is not in the repository. The tool server's code is public in tt-decomp, but its data is local to its author. Lane F confirmed that whole-image function lists exported from Ghidra were removed from tracking on 21 January and are local only. What is tracked is a configuration with 142 hand-listed function entries and 9 runtime-library entries, built with IDA Pro, Hex-Rays and signature matching. Inferred The database producer is IDA Pro with Hex-Rays.
  • Verified Real class names exist: RTTI scans show a CBaseDC hierarchy of 108 child classes and rage:: allocator classes. No real function names were found in any file opened. Function references are address-derived labels, and semantic names were assigned by people. Assertion file paths and Class::Method debug strings in the executable are secondary name sources.
  • Function counts differ by pipeline. Inferred 31,782 is the IDA figure. Verified 35,888 is one port's recompiled count and 36,409 is parsed from generated C++ in tt-decomp. The PC count is not yet measured.

Documents worth reading

  • Asset streaming. Camera to a registry of 24-byte records, 8 load slots, ring buffers and fixup callbacks. It uses five evidence labels, which this project copied.
  • RAGE API README. The rage:: and GTA4:: class lists. Many entries are stubs, and weapons and pathfinding are listed as to-dos.
  • RTTI and HUD handles, for the method of building class-to-virtual-table tables.
  • Collision aliasing postmortem, which shows the collision pipeline and that RAGE physics is built on Bullet. Inferred for the PC build.
  • Shader pipeline and reflection study, for the renderer phase.
  • Verified Not found: Euphoria notes, script VM internals, a main-loop document. These projects treat game logic as a black box. Reads truncated at about 11 to 16 KB, so several long documents were seen only in part.

Carrying names across by slot order

  • Verified tt-decomp matched GTA IV against Rockstar Table Tennis, both PowerPC, in three passes. Exact normalised instruction hashes matched 0 functions. Virtual table slot position matched 5 of 5, all rage::grcSetup at 85% confidence. Prologue hash plus Jaccard similarity of at least 75% matched 0. The run took 7.6 seconds over 36,409 against 7,161 functions (report).
  • Inferred Slot order does not depend on the instruction set, so it should work from the 360 binary to the PC binary. Instruction hashes will not. No PowerPC to x86 matcher was found. Class names, slot counts, assertion paths and string constants should also survive, but none is yet checked on the PC binary.

Licences and state

  • Verified LibertyRecomp, UnleashedRecomp and MarathonRecomp are GPL-3.0. XenonRecomp and XenosRecomp are MIT, ReXGlue is BSD-3-Clause, and one independent port has no licence file and counts as all rights reserved.
  • Verified OZORDI/LibertyRecomp is the active line (last commit 2026-09-23) and is moving to a native GTA IV renderer. The independent luisxl15 port reached gameplay except collision and is paused. Lane D suspected its collision bug was the one OZORDI later fixed. Lane F found its cause still unknown (see the next entry).

What went wrong for the recompilation projects, and what we take from it

Most of the bugs these projects hit are specific to translating PowerPC code and emulating the Xbox 360 kernel, and do not apply to a PC rewrite. The patterns around those bugs do apply: stubs that became permanent, a renderer that took months, a misdiagnosis that took weeks, hooks that broke what they instrumented, wrong addresses that failed silently, and research that was deleted. The table gives each pattern and what we do about it.

What lane F read

  • Verified Lane F listed all 240 GTA-era commits on the main branch of OZORDI/LibertyRecomp by title and date and read about 35 key commits in full. Its GitHub API access returned 403, so it used commit feeds, patch files and raw files. Each item is labelled Verified (opened and read) or Inferred (deduced from a list, a snippet or an absence), and this entry keeps those labels.
  • Verified The main line ran from 13 December to 9 March and then froze. A development line carried the work from January to August and replaced main by force-push on 14 August (pull request 5). An earlier force-push on 26 January rewrote every commit hash back to the Sonic port the project was forked from.
  • Verified The independent port by luisxl15 has six commits, all on 7 and 8 August 2026. It boots all 35,888 functions, renders the opening cinematic and reaches interactive gameplay with HUD and radar, but static world collision never loads, saves are rejected by the menu, and it has had no commits for about two months. Four other forks hold no work of their own except one continuous-integration fix. Their value is that they preserve commits and documents the main repository later dropped.
  • Verified Boot to initialisation took about 15 days (13 to 28 December), and frames to a stable run took 8 more. Audio was built on 1 January, deleted on 15 April and rebuilt from July to September.
  • Inferred In-game visuals came only with the native renderer promoted on 14 August. No drawn-content milestone was found between January and July.

Patterns and what we do about them

Pattern What happened to them What we do
Stubs became permanent Verified Seven subsystem initialisers that blocked on console synchronisation were stubbed on 28 December as temporary. Native replacements were never verified. A loading-gate bypass after 500 iterations has no later real implementation that lane F could find (removal could not be verified either). AGENTS.md rule 3 bans stubs presented as implementations. A function that cannot be done is deferred with a blocker tag, so it stays visible in the queue and the ledger, counted as not rewritten. Deferred functions go to a second pass on a different model.
Rendering is the long pole Verified A purple screen on 7 January meant the GPU path was alive but showed nothing. First-draw research ran from January to April and ended in a revert. Playability came only with a rewritten renderer. The renderer is its own phase with its own exit gate (frame rate measured on all three platforms), not a tail task. A Direct3D 9 present hook has already been verified on GTA IV by the d3d9capture project, which helps early capture.
Weeks-long misdiagnosis Verified A crash was labelled an audio use-after-free and drew a 14-agent investigation. The supposed poison value was a legitimate light-grey HUD colour, the audio frame was the shared immediate-mode draw batcher, and the real bug was a render hook that had never been installed. The synthesis refutes the audio label and one sibling agent's claim. A fix needs proof of the cause first (a log comparison or a caller graph). The emulator comparison reproduces a single function from a recorded state, so a fault is attributed to a function, not to a guessed subsystem.
Hooks broke what they instrumented Verified A hook that bypassed the original's frame-counter increment killed frame pacing after 5 frames. Another hook zeroed a submitted-frame counter, so presentation stalled after frame 2. 44 hooks inherited from the Sonic port matched nothing in GTA IV, and about 100 diagnostic hooks were removed on 11 April. The emulator comparison checks memory writes and outgoing calls, so a missing side effect shows as a disagreement. The per-function switch isolates a bad replacement.
Wrong addresses failed silently Verified Wrong addresses for two C runtime copy functions silently corrupted 149 and 161 call sites and surfaced as a null crash elsewhere. Later fixes covered 13 bad code-generation addresses, 11 mid-function splits and an offset formula that mixed two address bases. The lint bans hard-coded original addresses, references resolve by symbol, and structures carry size and offset assertions. Function boundaries are as much a risk for us, so a wrong boundary must fail loudly in the comparison.
Rendered but not collidable Verified Both projects fell through roads that looked intact. OZORDI's cause was a translator miscompile of an aliasing form of a vector pack instruction in the physics broadphase, fixed on 21 August (postmortem). luisxl15's cause is unknown after seven ruled-out hypotheses (notes). The notes say the same symptom reportedly appears in an emulator but not on native PC. Inferred That hint points to timing or environment, and the underlying truth is unconfirmed. Build an end-to-end collision test early (a body standing on a loaded road). A miscompile cannot occur in our code, but the streaming path that supplies collision data can fail in the same way.
Async reads served synchronously Verified LibertyRecomp serves even asynchronous file handles synchronously, with a hard-coded true in the condition. The game's streaming depends on completion events, callbacks and pending states, which this shortcut hides (streaming document). Model asynchronous completion in our file layer from the start, and give any shortcut an expiry date. Confirm how the PC file layer completes reads before writing it.

Causes specific to translating PowerPC code

  • Verified A nine-worker startup deadlock from unsignalled semaphores and kernel tasks that exited early. Console synchronisation primitives never satisfied on PC, which blocked the loading gate, the HUD and 63-subsystem initialisation. Host and guest thread-local storage that diverged. A defensive write inside the kernel import region that corrupted imports and read as vtable failures. C runtime start-up callbacks. A vertical-blank timer and timebase that froze loading. A translator miscompile in physics.
  • The knowledge that carries over is which subsystems wait on synchronisation and in what order the engine initialises (rewrite playbook).

Engine behaviours to confirm on PC, not assume

Verified The projects documented the following for the Xbox 360 build. Unknown Each is unconfirmed for the PC build, which was designed around different memory and a different thread model. Sources: runtime behaviour, the playbook above, the streaming document and the rendering research.

  • Boot: the engine's entry function runs once, where the console runtime called it repeatedly and a recompilation must supply the loop. Then a frame tick, a ready check, a call that starts nine workers and the subsystems, one call that initialises 63 subsystems, a loading gate, and a main loop under an orchestrator that ends in a present.
  • Threads: nine workers (two render, three streaming, three resource, two GPU), a special thread with a 256 KB stack, a vertical-blank path, an audio stream worker and a separate audio render driver, and content-enumeration threads. The render workers block by design.
  • Streaming: a registry of 24-byte records with a four-state machine, recursive dependency acquisition, 8 fixed load slots, a synthetic stream path by index, per-worker rings of 16 positions (15 usable, reads up to 32 KiB), file-device layers for disc and hard-disk cache, and per-type fixup callbacks. Scripts gate on a native that pauses for streaming, and reads use overlapped I/O.
  • Timing: a 50 MHz guest timebase (a wrong value freezes every time-gated loading task), a 60 Hz vertical blank, a present gate that stalls when submitted frames exceed presented frames by 2, a frame counter in the device, and cooperative-polling status codes.
  • Render path: a RAGE layer over a Direct3D-style wrapper over command packets; immediate-mode draw begin, add-vertex and end; HUD draw commands as a 108-class hierarchy in a per-frame bump arena whose allocator sits in a thread-local slot; six named reflection resources (mirror at 320 by 180, environment paraboloid at 256).
  • Collision: load and fixup, composite expansion, bounding-volume bodies, simulation identifiers, a deferred insert queue, world bounds, axis-sweep quantisation, endpoint sort, a pair cache, filtering and narrowphase. The title-update build keeps a 500-slot bounds store with a flag-byte state machine scanned every frame (collision document).
  • Unknown Which script threads must run for the world to appear. Neither project documented it. Only the registration of script natives was mapped.

Working with agent lanes: what we learned

A lane is one agent working on one task in its own folder. The eight research lanes worked, but a lane that cannot run shell commands is limited to web reads, and long files were read only in part. Requiring every finding to be marked Verified or Inferred made checking cheap and is now a project rule.

Running Muse Spark lanes

  • Verified The command is muse exec --model muse-spark-1.3-contributor --reasoning-effort max --approval-mode never --workspace <folder> --prompt-file <file>. Output appears only when the lane exits. Lanes took 15 to 60 minutes.
  • Verified In an untrusted workspace the lane could not run shell commands, so it could not clone repositories. Fix before phase 1 (muse sandbox, workspace trust).
  • Verified Web reads truncate past roughly 11 to 16 KB, so long files were only partly read. The GitHub API rate-limited one lane.
  • Verified Two of lane A's claims were checked against the source files and matched exactly. Lane H (dependencies) was mostly inferred from forum posts and said so. Lane F, whose GitHub API access returned 403, read history through commit feeds, patch files and raw files instead, and labelled each item.

Generating placeholder images with Codex

  • Verified The image generation feature is enabled in the CLI. The lane got a small workspace (the docs folder), because large writable roots stall its sandbox on this machine.
  • Verified The brief told it to begin every shell command with Set-Location. Six 1600 by 900 WebP images took about fifteen minutes.
  • Every generated image on the site is captioned as a concept image, not a screenshot.

Practices from other agent projects

  • Task size. Verified Thief 3 sizes work by function length, keeps workers under about 100 tool calls and never reuses a worker. Inferred The sources give the limits, not the reason. Our reading is that context decays in long sessions, so a fresh worker with a full packet beats a long session.
  • Guard rails in tooling. Verified Thief 3 and Snowboard Kids 2 enforce permissions with hooks, so a worker cannot edit the checker or generated files even when it tries. Our lane rules in AGENTS.md still need that enforcement in phase 1.
  • Claiming success without proof. Verified A Thief 3 survey says the verifier is the product, because agents cheat with inline assembly, edited checksums and lenient comparison rules. Thief 3 also sweeps for the opposite failure: a worker saw a passing result and never ran the acceptance step. Our rule: a machine check decides.
  • Verified Thief 3 workers change one thing per attempt, say what difference it targets, treat unchanged output as a no-op, and defer rather than guess.
  • Inferred The plan records that the Modern Warfare 2 project found mixed goals stalled its lanes, hence no 64-bit or renderer work before phase 4. The source is the coordinator's search, not a lane report.
  • Verified Both of the Modern Warfare 2 author's write-ups returned 404 when tried. That project's verification method, audit counts of wrong or faked functions, and agent scaling are unknown to us.
  • Verified A recompilation project's agents produced 54 research documents in one cycle with no change in behaviour. Count a lane's output in accepted functions, not pages. The recompilation entry has the details.

Upscaling, frame generation and ray-tracing denoisers

The four vendor frameworks cannot all be reached from one Vulkan renderer, and two of them are narrower than we assumed. The full reference, with a source link and a verified or inferred label on every claim, is the file documentation/upscaling-and-frame-generation.md in the repository. Read it before designing the renderer.

What changed in the plan

  • Verified DLSS 5 exists. NVIDIA's developer blog of 22 September 2026 describes it as neural rendering that needs an RTX 50 series GPU. The page does not say an SDK is available to developers, so the plan targets DLSS 4.5 through the Streamline SDK (NVIDIA developer blog). The coordinator opened this page.
  • Verified XeSS frame generation supports DirectX 12 only and works through its own replacement swap chain. XeSS upscaling supports Vulkan (XeSS frame generation guide). The coordinator opened this page.
  • Verified MoltenVK has no ray tracing in any release; the extensions exist only in an open pull request (MoltenVK pull request 2771). Path tracing on macOS therefore needs a native Metal backend.
  • Inferred DLSS is reported as unsupported on Windows on ARM64, and XeSS documents x64 only. FSR is the only candidate there and probably needs a rebuild from source.
  • Inferred MetalFX is reachable only through Metal. FSR on macOS is unconfirmed, so the macOS target lists MetalFX alone.
  • Verified Rust bindings: objc2-metal-fx is maintained; the DLSS and FidelityFX crates are new or placeholders; XeSS has none.

What the renderer must be designed for

  • Every temporal upscaler needs jittered low-resolution colour, depth, per-pixel motion vectors, exposure, and a reset signal on camera cuts.
  • Frame generation also needs the picture without the HUD, the UI separately, and control of presentation: DLSS, FSR and XeSS each bring their own swap chain.

What is still unknown

Unknown The exact motion vector, depth and jitter conventions of each framework. The research lane's web reads truncated before those sections of the long guides. A lane with a working shell should read them from cloned repositories before renderer design starts.
